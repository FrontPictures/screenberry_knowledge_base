# Screenberry Knowledge Base: практический план создания репозитория

Дата: 29 сентября 2026 года.

Статус: предложение для обсуждения разработчиками; описанные механизмы ещё не реализованы.

Исходные условия: текущая публичная версия Screenberry — 3.4; версия 3.5 находится в разработке.

## 1. Цель и основные решения

Создать общую, проверяемую и регулярно обновляемую базу знаний о Screenberry. Она должна служить источником для User Guide, встроенного AI Assistant, AI поддержки, Codex и внешних интеграций.

Рекомендуемый подход:

1. Хранить редактируемые знания в GitHub в Markdown с YAML-метаданными.
2. Хранить структурированные сведения о продукте в YAML/JSON с проверяемыми схемами.
3. Сохранить существующий MDX User Guide и постепенно подключить его к общей модели знаний.
4. У каждого факта должно быть одно основное место редактирования. Производные представления генерировать автоматически.
5. Разделять применимость знания к версии, степень его проверки и статус выпуска продукта.
6. Строить публичное руководство и поиск только из материалов, допустимых для выбранной версии.
7. Предоставить локальный доступ к файлам, публичный Markdown-экспорт и впоследствии общий поисковый API.
8. Проверять качество ответов на реальных вопросах пользователей.

Публикация репозитория сама по себе не подключает его ко всем AI. Каждый потребитель должен читать файлы, синхронизировать экспорт или обращаться к поисковому сервису.

## 2. Размещение и ответственность за источник

### Рекомендуемый старт

Начать в существующем репозитории документации. Он уже содержит `content/en/`, `content/jp/`, тематические MDX-страницы и инфраструктуру публикации. Добавить схему знаний, проверку версий и экспорт без массового переноса страниц.

Если нужен отдельный публичный репозиторий, возможны два решения:

| Решение | Правило |
| --- | --- |
| Репозиторий документации остаётся основным | Отдельный репозиторий знаний выпускается автоматически; ручные правки в нём не принимаются |
| Новый репозиторий знаний становится основным | Сайт получает материалы из зафиксированной ревизии; мигрированные факты редактируются только в базе знаний |

На старте рекомендуется первое решение либо один общий репозиторий. Переход ко второму оправдан, если база приобретёт собственный цикл разработки и отдельную команду.

Для каждой категории данных зафиксировать источник истины: например, типы и значения параметров приходят из экспорта продукта, а объяснения поведения и инструкции редактируются экспертами. Автоматически обнаруженные расхождения отправляются на проверку, а не разрешаются молчаливой перезаписью.

### Публичность

- Согласовать, разрешена ли публичная публикация сведений о разрабатываемой 3.5.
- Фильтрация User Guide не скрывает файлы и историю открытого GitHub-репозитория.
- Конфиденциальные материалы хранить в отдельном закрытом источнике; метка `internal` внутри публичного файла не обеспечивает защиту.
- Выбрать лицензию на документацию, примеры и изображения; явно описать условия повторного использования.
- Принимать внешние предложения через issues и pull requests; публикация требует проверки ответственным специалистом.

## 3. Предлагаемая структура

Ниже — целевая логическая структура. Это не требование немедленно переместить существующие MDX-файлы.

```text
README.md                      Назначение, способы доступа, начало работы
AGENTS.md                      Краткие инструкции AI по работе с репозиторием
CONTRIBUTING.md                 Правила внесения и проверки знаний
LICENSE                        Условия использования
releases.yaml                  Реестр версий и публичная версия по умолчанию
schemas/                       Схемы метаданных, сущностей и проверочных вопросов
knowledge/
  en/
    concepts/                  Устройство продукта и объяснения
    reference/                 Ноды, параметры, интерфейс, интеграции
    how-to/                    Решение конкретных задач
    tutorials/                 Последовательное обучение
    troubleshooting/           Диагностика и восстановление
    known-issues/              Известные ошибки и обходные пути
    compatibility/             Совместимость и ограничения
    releases/                  Описание изменений между версиями
    glossary/                  Названия и синонимы
  jp/                          Переводы с привязкой к ревизии оригинала
entities/                      Структурированные записи о продукте
examples/                      Проверенные проекты и конфигурации
assets/                        Изображения и другие связанные материалы
evals/                         Контрольные вопросы и критерии ответов
tools/                         Валидация, экспорт, сборка каталога
.github/
  workflows/                   Проверки и публикация
  CODEOWNERS                   Ответственные за области знаний
```

Каталоги Markdown, JSONL, `llms.txt`, поисковые индексы и manifest сборки — производные артефакты. Их следует выпускать автоматически, например в артефактах CI или GitHub Releases. Embeddings не являются редактируемым источником знаний.

## 4. Форматы и правила написания

| Данные | Основной формат |
| --- | --- |
| Объяснения, инструкции, диагностика | Markdown + YAML frontmatter |
| Существующий User Guide | MDX с автоматическим экспортом чистого Markdown |
| Типы, значения, диапазоны, связи сущностей | YAML или JSON с JSON Schema |
| Контрольные вопросы | YAML или JSONL |
| Иллюстрации и проекты | Отдельные файлы со ссылками из материалов |
| Каталог для интеграций | Генерируемый JSON/JSONL |

Правила для авторов:

- Один документ описывает одну связную тему, задачу или проблему. Не дробить каждое предложение в отдельный файл.
- Начинать с прямого объяснения назначения или результата.
- Для инструкции указывать условия, шаги, ожидаемый результат, проверку успеха и восстановление при ошибке.
- Для диагностики указывать симптом, различающие проверки, вероятные причины и решения.
- Записывать исключения и ограничения, включая неподдерживаемые сценарии.
- Использовать точные названия интерфейса; хранить пользовательские синонимы отдельно.
- Существенную информацию из GIF, видео и скриншотов описывать текстом.
- Ссылаться на связанные материалы вместо ручного повторения одного факта во многих статьях.
- Сохранять семантические заголовки, понятные ссылки и альтернативный текст изображений.

MDX-экспорт должен разбирать структуру документа, сохранять содержимое компонентов, таблиц и примечаний, убирать оформительские обёртки, разрешать относительные ссылки и сохранять доступ к изображениям. Неизвестные компоненты должны вызывать диагностическое сообщение, а не терять содержимое незаметно.

## 5. Метаданные и модель записи

Минимально необходимые поля: стабильный ID темы, язык, тип материала, применимость к версиям, статус проверки и ответственный. Для подтверждённых материалов обязательны сведения о проверке и доказательства.

Пример ниже иллюстрирует структуру, а не утверждает поведение конкретной функции:

```yaml
---
id: playback.example
variant_id: playback.example.since-3-5
title: Example playback behavior
language: en
kind: reference
status: draft
owner: playback-team
applies_to:
  from: "3.5"
  until_exclusive: null
verified_in: []
last_verified: null
evidence: []
aliases: []
related: []
---
```

| Поле | Назначение |
| --- | --- |
| `id` | Стабильный идентификатор темы, общий для редакций и переводов |
| `variant_id` | Идентификатор конкретной версии содержания |
| `language` | Язык; для японского — `ja`, хотя существующий каталог и URL используют `jp` |
| `kind` | Тип: reference, how-to, troubleshooting и т. д. |
| `status` | `draft`, `in_review`, `verified`, `withdrawn` |
| `owner` | Команда или роль, ответственная за корректность |
| `applies_to` | Границы применимости; дополнительно ОС, редакция, лицензия или оборудование, если существенно |
| `verified_in` | Конкретные версии/сборки, на которых проверен материал |
| `last_verified` | Дата фактической проверки содержания |
| `evidence` | Ссылки на спецификацию, воспроизводимую проверку или подтверждение специалиста |
| `aliases`, `related` | Синонимы и ссылки на связанные ID |

Уникальность записи определяется сочетанием `variant_id` и языка. Правка текста отслеживается Git; новое значение `variant_id` нужно при появлении отдельного варианта применимости, а не при исправлении опечатки.

Дата изменения файла не заменяет `last_verified`. Отсутствие верхней границы версии означает предполагаемую продолжающуюся применимость, но не проверку во всех будущих версиях.

Для сложных страниц сначала лучше создавать полные варианты статьи с общим ID. Условия на уровне отдельных утверждений вводить только при подтверждённой необходимости: большое количество условных фрагментов усложняет чтение и проверку.

## 6. Версии 3.4 и 3.5

### Реестр релизов

```yaml
default_public_version: "3.4"
releases:
  "3.4":
    status: released
  "3.5":
    status: development
```

Применимость знания, статус его проверки и статус релиза — независимые признаки. Материал о 3.5 может иметь статус `verified`, оставаясь недопустимым для публичного руководства 3.4.

### Правила выбора

1. Определить целевую версию продукта.
2. Определить разрешённый канал: публичный или внутренний preview.
3. Отобрать применимые варианты и допустимые статусы проверки.
4. Проверить отсутствие неоднозначных перекрытий вариантов одной темы.
5. Только после этого формировать руководство или выполнять поиск.

Версии сравнивать как версии, а не как строки или десятичные числа. До реализации согласовать правила patch-версий, prerelease и build ID. Если поведение зависит от конкретной сборки 3.5, одной метки `3.5` недостаточно.

| Сценарий | Политика |
| --- | --- |
| Публичный User Guide | Только проверенные материалы для 3.4 |
| Встроенный AI Assistant | Версия передаётся приложением автоматически |
| Поддержка | Версия клиента; уточнение, если она влияет на ответ |
| Внешний ассистент без версии | Публичная версия по умолчанию, сейчас 3.4 |
| Разработка и preview | Явный выбор 3.5; черновики только с соответствующей маркировкой |
| Сравнение версий | Отдельный явный запрос; результаты сохраняют маркировку версии |

Если поведение изменилось в 3.5, предыдущий вариант заканчивается перед 3.5, а новый начинается с 3.5. Неизменившийся материал не копируется без необходимости. Неизвестная применимость не должна автоматически считаться совместимостью.

### Ветки и публикация

- В `main` могут совместно находиться знания о 3.4 и 3.5.
- Слияние в `main` не означает переключение публичного руководства на 3.5.
- Публичная сборка явно использует `target_version: "3.4"`; preview использует 3.5.
- Долгоживущие ветки для каждой версии не являются основным механизмом хранения знаний.
- Каждая публикация фиксирует ревизию корпуса и версию продукта; для поддерживаемых старых версий доступны снимки или явно выбираемые представления.
- При выпуске 3.5 проверяются покрытие, перевод, ссылки и ответы, после чего меняется публичная версия по умолчанию.

## 7. User Guide и локализация

Сохранять существующие `/en/...` и `/jp/...`, canonical metadata, `lang="ja"` и навигацию `_meta.ts`. Публичные адреса без номера версии показывают текущую опубликованную версию. Адреса архивов и preview определить отдельно до внедрения.

Предлагается английский как основной язык фактов. Перевод хранит ID оригинала и ревизию, из которой выполнен. Изменение оригинала помечает перевод как требующий проверки.

Политику устаревших переводов нужно утвердить явно: задержка публикации, обозначенный переход к английскому или сохранение проверенного предыдущего содержания с предупреждением. Нельзя незаметно смешивать версии и языки.

Версионный отбор выполняется до сборки навигации, статических страниц, Pagefind и sitemap. Проверка только видимости в меню недостаточна: материал 3.5 не должен случайно появиться в поиске, экспорте, прямом публичном URL или sitemap руководства 3.4.

## 8. Доступ для AI и поисковая архитектура

Основной подход — поиск по актуальному корпусу с передачей найденных фрагментов модели (RAG). Дообучение можно позднее использовать для поведения и стиля; обновление продуктовых фактов обеспечивается источниками и поиском.

```text
GitHub: проверенные источники и реестр релизов
                    ↓
Проверка → отбор версии → нормализация → manifest
                    ↓
       ┌────────────┼───────────────┐
       ↓            ↓               ↓
   User Guide   Markdown/JSONL   Поисковый индекс
                                    ↓
                           API / MCP-обёртка
                                    ↓
                      Ассистенты и интеграции
```

### Три способа доступа

1. **Локальные файлы.** Для Codex и других агентов: понятная карта тем, `AGENTS.md`, поиск по файлам и выбор версии. Векторная база для этого не обязательна.
2. **Статический экспорт.** Публичные Markdown-страницы, каталог, manifest и скачиваемый пакет определённой ревизии.
3. **Общий поиск.** API для приложения, поддержки и внешних потребителей; при необходимости MCP как дополнительный интерфейс к тому же сервису.

Предлагаемые операции API, не существующие на данный момент:

```text
search(query, product_version, language, filters)
get_document(id, product_version, language)
get_manifest()
```

Права на закрытые источники проверяет сервер. Клиентский параметр не должен сам по себе открывать внутренние материалы.

Поиск должен сочетать точные совпадения названий, параметров и ошибок с семантическим поиском. Фильтры версии и допустимости применяются до ранжирования либо через заранее разделённые индексы. При отсутствии подходящего материала возвращается отсутствие данных, а не ответ из следующей версии.

Фрагмент результата содержит текст, ID документа, раздел, язык, применимость, статус проверки, URL источника и ревизию корпуса. Инструкции, предупреждения и таблицы нельзя разрезать так, чтобы терялся контекст. Размер фрагментов и число результатов подбираются на контрольных вопросах.

В ответах ассистент указывает источники и существенную версию, уточняет недостающие условия и различает подтверждённые сведения и предположения.

### AGENTS.md и llms.txt

- `AGENTS.md`: краткая карта репозитория, правила версий, источников и внесения изменений. Не помещать туда весь корпус.
- `llms.txt`: автоматически генерируемая точка входа со ссылками на доступные Markdown-материалы. Не считать гарантией использования базы внешними AI.
- Полный объединённый экспорт можно предложить для скачивания, но не передавать весь корпус в каждый запрос.

## 9. Обновление и проверка достоверности

Рабочий процесс:

1. Изменение продукта или новый вопрос поддержки создаёт задачу на знание.
2. Автор определяет затронутые сущности, версии, инструкции и ограничения.
3. Вносит изменения и фиксирует подтверждение.
4. Ответственный специалист проверяет факты; редактор проверяет ясность и структуру.
5. CI проверяет схемы, ссылки, варианты, экспорт и контрольные вопросы.
6. После принятия изменений собираются согласованные артефакты.
7. Публикуются сайт и индекс с отслеживаемой ревизией.

Release checklist продукта должен включать оценку влияния на документацию. Дополнительно нужны периодические проверки высокорисковых и часто используемых тем.

Вопросы из поддержки преобразуются в обобщённые материалы после удаления персональных и клиентских данных. Автоматический черновик не получает статус `verified` без подтверждения.

Индексация учитывает изменённые, удалённые, отозванные и заменённые записи. Желательно собирать новый индекс отдельно и переключать его после успешной проверки, сохраняя возможность отката.

Manifest сборки содержит commit SHA, целевую версию, ревизию схемы, время сборки и контрольные суммы документов. Нужны наблюдение за отставанием индекса, уведомление об ошибке публикации и определённый срок доставки принятого изменения потребителям.

## 10. Контроль качества

Начать с 50–100 реальных вопросов пользователей и поддержки. Для каждого хранить:

- вопрос, версию и существенные условия;
- обязательные факты ответа и допустимые источники;
- недопустимые утверждения;
- ожидаемое уточнение или признание отсутствия данных;
- идентификаторы тем для оценки покрытия.

Оценивать отдельно качество поиска и качество ответа. Проверять точные названия, перефразированные вопросы, разные языки, конфликт версий, отсутствие ответа, устаревшие материалы и инструкции с несколькими шагами.

Критические проверки для 3.4/3.5:

| Проверка | Ожидаемый результат |
| --- | --- |
| Функция существует только в 3.5; запрос для 3.4 | Не описывать её как доступную в 3.4 |
| Поведение изменилось в 3.5 | Выбирать вариант целевой версии |
| Материал 3.5 проверен, но релиз не выпущен | Не включать в User Guide 3.4 |
| Два конфликтующих применимых варианта | Ошибка валидации, а не случайный выбор |
| Черновик без доказательств | Исключение из публичного подтверждённого корпуса |
| Документ отозван или удалён | Удаление его фрагментов из активного индекса |
| Перевод относится к другой ревизии | Выявление расхождения и применение утверждённой политики |
| Версия неизвестна | Явное применение публичной версии либо уточнение |

Метрики: доля вопросов с найденным правильным источником, корректность фактов и ссылок, число ошибок применимости, полнота покрытия, задержка обновления индекса и время ответа. Целевые значения согласовать после измерения пилота; утечка знаний будущей версии в публичные ответы считается блокирующим дефектом.

## 11. Дополнительные сценарии

- Контекстная помощь по выбранной ноде или параметру.
- Объяснение ошибок по диагностическим данным.
- Подготовка операторов и пошаговое обучение.
- Проверка конфигурации проекта перед показом.
- Объяснение изменений и помощь при переходе между версиями.
- Подготовка ответов поддержки со ссылками на подтверждения.
- Поиск пробелов в документации по неотвеченным вопросам.

Для диагностики текущего проекта и выполнения действий дополнительно нужны живое состояние Screenberry и инструменты управления с соответствующими правами. База знаний не заменяет эти интерфейсы.

## 12. Этапы внедрения и критерии готовности

### Этап 1. Согласовать контракт

- [ ] Выбрать основной репозиторий и владельцев разделов.
- [ ] Определить публичность знаний о 3.5 и лицензию.
- [ ] Утвердить метаданные, статусы и сравнение версий/сборок.
- [ ] Утвердить источники подтверждений и правила переводов.
- [ ] Зафиксировать реестр релизов и публичную версию 3.4.

Готовность: разработчики и авторы одинаково понимают, где редактировать факт и когда он допускается к публикации.

### Этап 2. Реализовать пилот

- [ ] Выбрать один раздел, например Media Player.
- [ ] Подготовить справку, задачи, диагностику и ограничения.
- [ ] Добавить подтверждённые примеры различий 3.4/3.5, если они есть; тестовые фикстуры не выдавать за факты продукта.
- [ ] Реализовать валидацию, выбор версии и Markdown-экспорт.
- [ ] Собрать контрольные вопросы и проверить ответы.

Готовность: один раздел полностью проходит путь от источника до версии руководства и ответа с корректной ссылкой.

### Этап 3. Подключить публикацию и потребителей

- [ ] Выпускать manifest, каталог, Markdown и llms.txt.
- [ ] Настроить CI, preview 3.5 и публичную сборку 3.4.
- [ ] Проверить навигацию, ссылки, Pagefind, sitemap и локализацию.
- [ ] Подключить первого ассистента; зафиксировать версию и ревизию в диагностике.
- [ ] Реализовать обновление, удаление из индекса и откат.

Готовность: принятая правка достигает потребителя предсказуемо, а содержимое 3.5 не попадает в представление 3.4.

### Этап 4. Масштабировать

- [ ] Расширять корпус по частоте вопросов и риску ошибок.
- [ ] Подключить общий поиск; добавить MCP при наличии потребителей.
- [ ] Автоматизировать сверку с экспортом параметров продукта.
- [ ] Расширить набор до 50–100 вопросов и закрепить проверки в CI.
- [ ] Включить обновление знаний в процесс выпуска Screenberry.

Не начинать с собственного сложного поискового стека, тотального переноса контента или дообучения модели. Сначала подтвердить качество знаний, выбора версии и экспорта на пилоте.

## 13. Вопросы для решения разработчиками

1. Разрешены ли публичные знания о 3.5 до релиза?
2. Остаётся ли текущий репозиторий главным источником или создаётся самостоятельный?
3. Какие сведения можно получать из продукта автоматически и кто отвечает за их точность?
4. Как приложение передаёт ассистенту версию, build ID и контекст проекта?
5. Какие предыдущие версии продукта необходимо обслуживать?
6. Как публиковать переводы, если они отстают от основного языка?
7. Какие способы подключения поддерживает существующий AI Assistant?
8. Каковы ограничения на хостинг, внешние AI-сервисы, стоимость и время ответа?
9. Кто утверждает знания, какие изменения блокируют релиз и как быстро обновляется индекс?
